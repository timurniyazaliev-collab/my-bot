# Подключение CRM «Sales» — что отдать разработчикам

Два способа подключить ИИ-менеджера к CRM. Решает не CRM-разработчик
сам по себе, а то, что реально умеет их система — стоит уточнить у них
на встрече, какой вариант им удобнее.

## Вариант А. Готовый вебхук (рекомендую)

У бота уже есть весь "мозг" продаж — факты о проекте, ответы на
возражения, когда передать лида менеджеру, какие фото прислать. Вебхук
(`webhook_server.py`) открывает этот мозг наружу одним адресом: CRM
присылает туда сообщение клиента, в ответ получает готовый текст +
флаг "пора звать менеджера" + ссылки на нужные фото. CRM-разработчикам
почти ничего не нужно писать самим — вся логика продаж уже готова и
проверена в Telegram.

Что отдать разработчикам:
- Адрес: `https://<домен>/api/lead-reply`
- Ключ доступа (`X-API-Key`) — отдельный секретный ключ для CRM, не
  Anthropic-ключ. Смотри "Как запустить" ниже.

### Основной метод: POST /api/lead-reply

Запрос (CRM → нам):
```json
{
  "conversation_id": "уникальный id диалога в CRM — обязательно",
  "message": "текст последнего сообщения от лида — обязательно",
  "channel": "whatsapp | telegram | instagram | facebook | website — необязательно, сейчас ни на что не влияет, просто для логов",
  "lead": {"name": "необязательно, сейчас не используется", "phone": "необязательно, сейчас не используется"}
}
```
Заголовок: `X-API-Key: <ключ>`.

Ответ (мы → CRM), синхронно, в том же HTTP-ответе — колбэков на
сторонний адрес нет:
```json
{
  "reply": "текст, который нужно показать клиенту",
  "escalate": false,
  "escalation_card": null,
  "photos": [
    {"category": "exterior_yard", "urls": ["https://.../media/exterior/yard_01.jpg"]}
  ],
  "unknown_questions": []
}
```
- `escalate: true` — единственная "команда" помимо текста: пора снять
  бота с диалога и подключить живого менеджера. `escalation_card` —
  карточка лида с деталями для него (текст, не структура). Других
  команд (создать сделку, сменить стадию, запросить контакт) бот
  сейчас не возвращает — это на стороне CRM после эскалации.
- `photos` — какие фото/планировки прислать клиенту и прямые ссылки
  на файлы (CRM скачивает по ссылке и отправляет клиенту тем же
  каналом). Голосовые/видео бот не отправляет.
- `unknown_questions` — вопросы клиента, на которые бот не нашёл
  ответа в базе (клиенту уже ответили "уточню"). Показывать отдельным
  списком, чтобы дополнять базу знаний.

Диалог CRM ведёт по `conversation_id` — сервер сам хранит историю
переписки (на диске, переживает перезапуски сервиса), CRM не обязана
присылать её целиком каждый раз.

Важный нюанс: пока диалог ведёт человек-менеджер (бот выключен из
диалога), наш сервер не видит эти сообщения — CRM их не присылает.
Если после этого снова включить бота на диалог, он не будет знать, что
говорил менеджер. Чтобы это исправить — перед повторным включением
бота CRM может вызвать `POST /api/conversation/<conversation_id>/sync`
и передать последние сообщения (в том числе от менеджера), чтобы бот
получил актуальный контекст:
```json
{
  "messages": [
    {"role": "user", "content": "Здравствуйте, ещё интересует рассрочка"},
    {"role": "assistant", "content": "Да, рассрочка на 26 месяцев"}
  ]
}
```
Это полностью заменяет сохранённую историю по этому `conversation_id`
(держим последние 30 сообщений). Не обязательно использовать, если
сценарий "бот отвечает после менеджера" не нужен.

Время ответа: обычно 2-8 секунд (модель Claude Opus), может доходить
до ~20-30 секунд при нагрузке на сторону Anthropic. Жёсткого таймаута
на нашей стороне нет — рекомендуем ставить таймаут запроса у CRM не
меньше 30 секунд.

### Ошибки

- `401` — неверный или отсутствующий `X-API-Key`.
- `400` — не передан `conversation_id` или `message`.
- `500` — внутренняя ошибка (например, сбой на стороне Anthropic).
  Сообщение клиента при этом не портит историю — можно повторить запрос
  ещё раз. Если бот недоступен — рекомендуем CRM сразу передавать
  диалог оператору, а не оставлять клиента без ответа.

Жёсткого лимита запросов в секунду нет, но сервер маленький (512 МБ
RAM, один процесс), нагрузочно не тестировался — при росте объёма
диалогов стоит заранее предупредить, чтобы успеть расширить сервер.

### Дополнительные методы

- `GET /health` — проверка, что сервис жив: `{"status": "ok"}`.
- `POST /api/reset` — сбросить историю диалога:
  `{"conversation_id": "..."}` → `{"status": "reset"}`.
- `GET /api/conversation/<conversation_id>` — получить сохранённую
  историю диалога (для отладки).
- `POST /api/conversation/<conversation_id>/sync` — заменить сохранённую
  историю диалога переданными сообщениями (см. пример выше) — для
  сценария "бот отвечает после того, как диалог вёл менеджер".

### Аналитика (для Тимура, не для CRM)

Эти методы не нужны разработчикам CRM для интеграции — это способ
самим посмотреть, как бот справляется, без захода в саму CRM:

- `GET /api/stats?date=2026-09-10` — сколько новых диалогов началось в
  этот день и сколько раз бот не знал ответа. Без `date` — за сегодня.
- `GET /api/conversations?date=2026-09-10` — список диалогов за день
  (id, число сообщений, время создания). Без `date` — последние 100
  диалогов. Полный текст конкретного диалога — через уже описанный
  `GET /api/conversation/<id>`.
- `GET /api/unknown-questions?date=2026-09-10` — вопросы клиентов, на
  которые бот не нашёл ответа в базе знаний, с привязкой к диалогу —
  сюда стоит заглядывать, чтобы понять, что дополнить в `zhk_dubai.md`
  или `lead_manager.md`. Без `date` — последние 200 записей.

Диалоги, начатые до этого обновления (когда время создания ещё не
записывалось), в выдаче по конкретной дате не появятся — это нормально,
это старые записи без даты.

### Тестирование

Отдельного тестового ключа/окружения не требуется: сервер полностью
изолирует диалоги по `conversation_id`, так что для отладки достаточно
слать запросы с любым тестовым id (например, `test-crm-1`) — это никак
не пересечётся с реальными лидами. Технический контакт по вопросам
интеграции — Тимур, вопросы передаются разработчикам через него.

### Безопасность

- API работает по HTTPS через домен (не голый IP) — обязательно к
  моменту интеграции.
- Ключ доступа передан один раз в переписке — после завершения работ
  будет перевыпущен новый, старый отключится.
- Ограничение по IP разработчиков CRM можно добавить дополнительно —
  пришлите статический исходящий IP вашего сервера, добавим в белый
  список.

### Как запустить (сделать один раз на сервере)

1. Сгенерировать секретный ключ для CRM (не Anthropic-ключ, а свой):
   `python3 -c "import secrets; print(secrets.token_urlsafe(32))"`
2. Добавить в `.env` на сервере (`/root/my-bot/.env`):
   `WEBHOOK_API_KEY=<сгенерированный ключ>`
3. Запустить `webhook_server.py` как отдельный сервис (по образцу
   `mybot.service`), например `mybot-webhook.service`, слушает порт
   8000 по умолчанию (`WEBHOOK_PORT` можно поменять) — порт наружу не
   открываем, только для nginx на самом сервере (localhost).
4. Публичный HTTPS-адрес: домена нет — используем бесплатный
   `<IP-сервера-через-дефис>.nip.io` (например, `178-62-243-159.nip.io`
   для IP `178.62.243.159`), он автоматически резолвится в IP сервера.
   Ставим nginx как обратный прокси (порты 80/443 → localhost:8000) и
   бесплатный сертификат Let's Encrypt через certbot. Порт 8000 закрыт
   для внешних подключений — снаружи доступен только nginx.

Когда появится нормальный домен (например, для сайта ЖК Dubai) —
переезд на него простой: меняем имя в nginx и перевыпускаем
сертификат, для CRM это просто новый адрес.

## Вариант Б. Просто дать доступ к Claude напрямую

Если у CRM «Sales» есть встроенная функция "подключить свою нейросеть"
(просто поле для API-ключа и системного промпта, без вебхука) — тогда
это быстрее всего.

1. Получить отдельный ключ Anthropic (не тот, что уже стоит у бота —
   чтобы CRM не могла случайно сломать или объесть лимит Telegram-бота,
   и чтобы ключ можно было отозвать отдельно):
   - Зайти на https://console.anthropic.com
   - Settings → API Keys → Create Key
   - Назвать понятно, например `crm-sales-2026`
   - Скопировать ключ (он покажется один раз) и отправить разработчикам
2. Сказать им модель: `claude-opus-5`
3. Дать текст системного промпта — это содержимое `lead_manager.md` +
   `zhk_dubai.md` (можно просто переслать оба файла).

Важно: в этом варианте вся логика — когда передавать лида менеджеру,
когда и какие фото присылать, память переписки — CRM-разработчикам
придётся писать заново внутри CRM, потому что просто ключ и промпт
этого не умеют сами по себе. Наш промпт сейчас рассчитан на вариант А
(в нём есть технические метки для эскалации и фото) — если выбираете
вариант Б, эти метки в промпте разработчикам либо нужно убрать, либо
научить CRM их понимать. Дай знать, какой вариант выбрали — при
необходимости адаптирую промпт под вариант Б отдельно.
